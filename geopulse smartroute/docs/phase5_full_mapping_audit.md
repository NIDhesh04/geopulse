The 700 traffic segments do **not** form a connected graph by themselves (they fragment into 221 disconnected components across Bhubaneswar).  
Therefore:
1. Dijkstra routing **cannot** be restricted to mapped traffic edges alone.
2. The routing engine **must** run on the full 46,679-edge Bhubaneswar OSM network (`bhubaneswar_drive.graphml`).
3. Unmonitored OSM edges must retain static baseline traversal times derived from speed limits ($t = d / v_{\text{freeflow}}$).
4. Mapped edges ($n = 657$) receive real-time and predicted dynamic edge weights from GeoPulse.

## J. Final Engineering Recommendation

### Selected Recommendation: **B. Mapping is mostly reliable but requires a targeted cleanup of specific segments before routing.**

**Evidence-Based Justification:**
1. **High Overall Quality:** 593 out of 700 segments (**84.71%**) map with `HIGH` confidence, achieving $0.00\text{ m}$ length error and sub-meter centroid distances.
2. **Identified Edge Cases:** Exactly 92 segments reside on two-way streets where direction is ambiguous without sensor heading, and 43 directed edges are mapped by duplicate sensor pairs.
3. **Actionable Pre-Routing Cleanup:** Before running dynamic Dijkstra routing, a simple deterministic policy can resolve these cases:
   - For duplicate sensor pairs, average their observed/predicted travel times.
   - For ambiguous two-way segments, assign the dynamic weight symmetrically or select the dominant flow direction.
   - For routing graph construction, embed all mapped edges into the full 46,679-edge network with static baselines on unmonitored links.
